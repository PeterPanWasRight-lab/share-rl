## 一、SDK 放置位置决策

**问题**：HRCrobot 厂家 SDK 应该放哪里？

**结论**：`src/share/robots/HRCrobot/vendor/HRCrobotSDK/`。

理由：
- 限定在机器人插件内部，不污染 `share` 主命名空间
- `controller.py` 已设计为"唯一接触 SDK 的点"，接入改动最小
- `vendor/` 目录名明确表达"第三方代码，升级时原样替换"
- 首选方案本应是 pip 依赖（对齐 UR 的 `rtde_control` 做法），但该 SDK 只有源码包，故走 vendor

不选的位置及原因：`src/share/utils/`（通用工具语义不符）、`hardEncodedScripts/`（脚本性质）、仓库根目录（已有大量文档，不再堆代码）。

注意：vendor 里有备份文件（`libpyhstrajproxy.so40ms`、`libpyhstrajproxy0402正常的`、`.pyc`），建议清理或加 `.gitignore`。

## 二、controller.py 接入 vendor SDK

### 2.1 SDK 两条独立链路

```
本体位姿/运动：hsrosi (HRCController) → libpyhstrajproxy.so → 端口 9095
夹爪 IO：     libhsc3.so（独立 ctypes 封装 _HSC3IOClient）→ 端口 23234
```

夹爪控制方式：双 IO 互斥——`DO25=1, DO26=0` 打开；`DO25=0, DO26=1` 闭合。

### 2.2 SDK 使用要点

1. **连接时序**：`init()` → `connect(ip, port, motion_mode="cartesian")`，SDK 自动以当前位姿启动笛卡尔模式（模式声明，不产生运动）
2. **SDK 无 servoL**：只有"到达目标位置"的 move。用 `move_to_cartesian_position` 流式下发 + 限频逼近伺服跟随（`example_externAix.py` 的 Z 轴小步示例印证）
3. **反逻辑返回值**：C 库 `HRC_move_to_d_pos` 返回 0 才算成功，hsrosi 已封装（内部 `result = not ...`），我们按"返回 True 成功"用
4. **动态库加载**：`libhsc3.so` / `libpyhstrajproxy.so` 的 RUNPATH 是相对路径 `./lib`，加载期间需短暂 chdir 到库目录（原示例的技巧），controller 已封装
5. **单位换算**：SDK 是 mm + euler 度（extrinsic XYZ）；适配层契约是 m + rotvec rad。换算隔离在两个纯函数 `_sdk_pose_to_rotvec_pose` / `_rotvec_pose_to_sdk_pose`，真机标定后若约定不同只改这两个函数
6. **`hsrosi` 是运行时动态导入**：vendor 目录通过 `sys.path` 注入，延迟 import，缺包时抛带提示的 ImportError

### 2.3 夹爪降级策略

HSC3 连不上时：只 warning + 记录命令状态，**不影响本体运动**。`use_gripper=False` 可显式跳过夹爪链路。

### 2.4 发现的 SDK 缺陷

`get_io` 读回恒为 False（扫描 0~63 号口全部验证）。**set_io 下发真实有效**（物理动作确认），但读回不可用于逻辑判断。疑为固件读的是 DI 空间或不支持 DO 读回。

## 三、限频机制精确语义（frequency）

`config.frequency = 100.0` → controller 内部 `period = 10ms`。**全代码库唯一的节拍限制点**是 `servo_cartesian()`（约 480-513 行），核心三段：

1. **等待**：调用太早 → `time.sleep` 到节拍点
2. **推进**：发完 `_next_servo_time += period`（固定推进，非 now+period，误差不积累）
3. **掉拍保护**：落后超 2 周期 → 节拍重置到当前时刻，丢弃过期目标，不补发

### 精确行为表

| 上层调用间隔 | 行为 |
|---|---|
| ≥ 10ms | 立即下发，零阻塞 |
| < 10ms | **阻塞到节拍点再发（点位永不丢弃）**，单次阻塞 ≤ 一个周期 |
| 掉拍 > 2 周期 | 立即发 + 节拍重置 |
| 未连接 | 抛 RuntimeError |

关键推论：
- `servo_cartesian` 是同步函数，**返回即已发出**，无后台排队
- 上层快慢抖动只转化为单次阻塞长短，**长期平均频率严格 = frequency**
- 不限频的接口：`get_tcp_pose` / `set_gripper` / `set_task_frame`（纯内存）/ `connect` / `disconnect`
- **无点位 buffer**：即发即弃，唯一内部状态是节拍时间戳。轨迹连续性责任在调用方；调用中断机器人停在最后目标附近，无库存可消耗
- SDK 层（`libpyhstrajproxy`）内部有周期转发机制但不透明（`*.so40ms` 备份暗示 40ms 周期变体存在），按"每次下发刷新目标"使用

## 四、while True 循环节拍实测

测试设计：满速循环 + 每拍 send_action，统计迭代周期。

**实测结果**（254 迭代 / 2.53s 墙钟）：

```
迭代周期         min=3.24  p50=9.91  p95=11.21  max=12.13  mean=9.96  ms
  get_observation  min=0.24  p50=0.34  p95=0.86   max=2.88   mean=0.41  ms
  send_action      min=2.61  p50=9.41  p95=10.81  max=11.80  mean=9.54  ms
平均下发频率 = 100.4 Hz
```

**结论**：
- 循环被 servo **精确锁相**到 10ms（p50 9.91 / 100.4Hz）
- `send_action` 的 p50 9.4ms 几乎全是限频等待，真下发仅 ~0.3ms
- min≈3.2ms 的迭代是节拍点刚过到达、无需等待的正常"呼吸"，锁相系统的正常现象
- 循环周期 ≈ max(10ms, 循环体自身耗时)——servo 保证下限，循环体保证下限
- **不要在循环里再加 sleep**（双重限速，两个节拍源互相错拍）
- 循环体自身开销 ≈ 0.75ms，10ms 预算里约 9ms 余量留给上层算策略

## 五、坐标系关系

### 5.1 层级

```
基座坐标系 (base, 由 SDK 定义)
    │  controller.get_tcp_pose() 报告 base→TCP（已换算 m + rotvec rad）
    ▼
"world"  =  base（恒等，SHaRe 直接采纳 base 当 world）
    │
    ▼  origin 平移/旋转
TaskFrame
    │
    ▼
{axis}.ee_pos   ← 上层 primitive 看到的数值
```

### 5.2 关键认知

- **SDK 返回的就是基座系读数**（不是某个抽象"世界系"）。base 是参考系本身，"世界系在哪"不可推断也无需推断（尺子量不出自己的原点）
- 真正需要标定的是 **TaskFrame.origin 相对 base 的位置**，三种方式：
  1. 入场快照（on_entry 读当前位姿当 origin）
  2. 手动示教读数写入配置（最常用）
  3. 外部固定帧标定（相机/桌面系，代码暂未支持）
- **origin 与 target 语义不同**：origin 定坐标系在哪；target 是不可学轴（`policy_mode=None`）的静态保持目标。origin 全零 ≠ target 全零
- origin 全零 = TaskFrame 与 base 重合 = 换算恒等（构造默认状态，不调 set_task_frame 即是）

### 5.3 TaskFrame 生命周期

- `set_task_frame()` **只保存不驱动机器人**（运动只发生在 send_action）
- 一个对象同时只持有一个当前帧（寄存器语义），primitive 切换时 env 层 `apply_task_frames()` 自动换写
- 下发时机三条路：primitive `reset()` / MP-Net 切换（先 `on_entry` 钩子改帧，再 `apply_task_frames()` 下发）/ `stop()` 紧急悬停（临时全零 RELATIVE 帧）
- 钩子改 env 里的帧 → apply_task_frames 推给机器人 → 才开始 step（顺序铁律）
- MP-Net 通过 `entry_context` 传递上一原语的 origin，保证跨切换帧连续性

## 六、安全要点

### ⚠️ 单轴下发的全零补齐陷阱

```python
# 危险！缺失的 x/y/rx/ry/rz 会被 task_frame.target（默认全零）补齐
robot.send_action({'z.ee_pos': 0.10})   # 机器人会冲向 base 原点、姿态转零位
```

正确写法：**每拍回填当前观测值锁定其余轴**：

```python
action = {f"{ax}.ee_pos": obs[f"{ax}.ee_pos"] for ax in AXES if ax != "z"}
action["z.ee_pos"] = target_z
robot.send_action(action)
```

或显式设置安全的 `task_frame.target`。

### 其他

- 机器人未使能时：连接/只读可做，运动测试需手动上使能
- 运动测试原则：小步长（0.1mm/拍）、快照起点、锁轴、绝对上限 + 墙钟超时、finally 保证断开

### 7.1 全链路闭环

|---|---|---|
| vendor SDK 加载 | ✅ | 离线布局测试 |
| 网络连接 | ✅ | 每次读取均有真实请求日志 |
| 位姿反馈 | ✅ | **上使能时抱闸释放，TCP 下沉 0.25mm 被捕捉**（缓存/桩数据不可能响应物理事件） |

关于"静止读数完全恒定"：工业控制器反馈量化 1µm，伺服锁住时臂端真的没有 1µm 以上运动，读数恒定是正常现象。区分真假的判据是**跨物理事件的响应**（如上使能下沉），不是会话内抖动。

## 八、两层架构的设计理由

`controller.py`（翻译官）与 `HRCrobot.py`（外交官）分离，因为**两类变化的速度和性质完全不同**：

| | controller.py | HRCrobot.py |
|---|---|---|
| 回答的问题 | 怎么跟这台硬件说话 | 怎么向 SHaRe 表达这个机器人 |
| 变化来源 | 厂家 SDK / 固件 / 单位约定 | 框架接口 / 任务语义 |
| 知识 | mm、euler、IO 口、端口、限频 | TaskFrame、feature 字典、LeRobot 协议 |

真实事件验证：
1. 旋转约定验证/修复只碰 controller 两个纯函数，上层零改动
2. HSC3 降级逻辑藏在 controller，上层对链路可用性无感
3. 限频放底层，primitive 循环完全不管节拍（while True 测试验证）
4. LeRobot 框架噪音（异常类、返回值惯例）不污染硬件代码

合成一层的后果：send_action 会同时混四种职责（框架检查 / 坐标换算 / 单位换算限频 / SDK 反逻辑处理），任何一层出 bug 都无法独立测试。
